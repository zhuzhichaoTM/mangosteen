### 顺带修的真实缺陷
**`/api/preview` 与 `/api/doctor` 双双超时**（本次启动时实测发现）：
两者都在请求路径上同步调 `probe_version()`，而 `llama-server --version`
在本机要 **27 秒**。`preview` 是云端费用确认弹窗的唯一数据源，一超时
用户就点不了部署。

修复方案是**带超时探测**（`ENGINE_PROBE_BUDGET = 2s`）：
| 情况 | 耗时 | 结论 |
|------|------|------|
| 缓存已有结果 | 0 | 直接给出 |
| 无缓存、引擎快 | < 2s | 现场探测并回填缓存 |
| 无缓存、引擎慢 | = 2s | 返回「未知」，不编造结论 |

为什么不「只读缓存」：服务刚启动缓存必空，坏引擎会被当成「本地可用」，
UI 说「不花钱」→ 实际降级云端计费，用户被意外收费。
实测：预热完成后 preview **48ms**，doctor **2.7ms**。

缓存也改为记录失败（`Result<String,String>`），预热线程失败时
调 `set_engine_failure`，这样下次不必再跑 27 秒就知道引擎坏了。

## 下载与资源评估解耦（修复 imatrix 下载被判失败）

### 用户报的问题
下载 `imatrix_unsloth.gguf` 后提示「登记模型失败：GGUF 格式错误……
元数据缺少必需字段 block_count / attention.head_count / embedding_length」。
文件其实**已完整下载**（13.6 MB），但整个任务被判 `failed`。

### 三层根因与修复
1. **状态语义错误（核心）**：`pulljobs::spawn` 把「登记失败」等同于
   「下载失败」。实际是两件事——传输成功 ≠ 能当模型用。
   - 新增 `PullJob.warning` 字段（≠ `error`，不代表失败）
   - 新增 `PullJobs::mark_done_with(id, model_id: Option, ..., warning)`
   - 登记失败 → `state = done` + warning「文件已下载完成（X），但无法登记为模型：…」
   - 前端三色提示：error 红 / warning 黄 / note 灰
2. **报错文案不可用**：原来只报「缺字段」，用户不知道是下错文件了。
   `gguf::extract_info` 现在**先看 `general.type`**：imatrix / adapter 等
   直接答「这不是可推理的模型文件，而是量化用的重要性矩阵（imatrix）数据」。
   `GgufInfo` 新增 `gguf_type` 字段。
3. **源头预防**：`is_auxiliary_gguf()` 在**远端列表阶段**过滤
   `imatrix` / `mmproj` / `lora` / `adapter` / `vocab`，以及**分片文件**
   （`-of-00002.gguf`，本项目单文件部署用不了）。
   用文件名而非读头部，因为此时文件还没下载。

### 顺带加的运维能力
- `DELETE /api/models/jobs` 清空**已终结**任务（运行中的保留——
  那是「取消」语义，删记录不能假装停了下载）
- 前端「下载任务」卡片加「清除已完成」按钮

### 清理
- 停掉所有后台服务与引擎实例（端口 11437 等全部释放）
- 删除磁盘上的 `imatrix_unsloth.gguf`（13.6 MB）
- 清空 1 条失败任务记录

### 测试
482 项全通过，零警告。新增：
- `download_success_with_register_failure_is_done_with_warning`（核心语义）
- `clear_finished_keeps_running_jobs`

### 教训
**「下载成功」和「能否当模型用」是两个独立状态。**
把后者失败映射成前者失败，会让用户以为白下了，而文件好好躺在磁盘上。
凡是「主流程成功、后处理失败」的场景，都该用 warning 而不是 error。

## 云端监控接入 + 部署页「算力来源」选择

### 1. 优云智算实例监控（GetCompShareInstanceMonitor）

**这个接口必须走 JSON 请求体**，表单编码全部被拒（真实调用对照实验）：

| 表单写法 | 厂商返回 |
|----------|----------|
| `UHostIds.0=uhost-x` | `210 Missing params [UHostIds]` |
| `UHostIds=["uhost-x"]` | `230 Params [...UHostIds] not available` |
| `UHostId=uhost-x`（单数） | `210 Missing params [UHostIds]` |

只有 `Content-Type: application/json` + 真 JSON 数组成功。**签名口径也不同**：
数组元素**直接首尾相接**（`UHostIdsu-1u-2`），逗号分隔或 JSON 字面量都会
`Signature VerifyAC Error`。见 `sign::signature_of_json`。

其他实测结论：
- 实例**关机时**接口正常返回 6 个 MetricKey，但每个 `Results` 都是空数组
  → 用 `DescribeCompShareInstance` 的 `MonitorMessages` 做兜底（含 CPU/内存当前值）
- `Data` 可能为 `null`（不是 `{}`），需 `de_object_or_null`
- `Region` 必填且必须与实例所在地域一致；驱动内先**不限地域**查实例定位地域再查监控
- 百分数 → 比例（0~1）的换算只在 `mapping::percent_to_ratio` 一处，多卡取最大值

### 2. 设备页签云端监控（后台采集 + 缓存）

`/api/sysinfo` 新增 `cloud` 段。**请求路径绝不调厂商接口**：设备页 2 秒轮询，
后台线程每 5 秒刷新一次写入共享快照，HTTP 只读内存（微秒级）。

三态必须可区分（混在一起用户找错人）：
- `supported: false` → 该服务商无监控接口
- `has_any: false` → 实例存在但厂商暂无数据（关机/刚开机）
- `error` → 调用失败，保留上次快照并提示

前端同时标注「数据新鲜度」：云端 5 秒缓存 vs 本地 2 秒采样，不标注会被当成实时值。

### 3. 修掉一个高危既有缺陷：curl 把同一请求发了两次

`mangosteen-cloud` 的 `CurlTransport::execute` 曾把 URL **同时**写进
`--config` 文件和 argv，curl 于是发两次请求，响应体变成
`{json}\n200{json}\n200`，解析报 `trailing characters at line 2`。

对 GET 只是「看起来怪」，**对 POST 创建实例意味着可能开出两台并持续计费**。
修复：URL 只走 argv。守护测试 `curl::tests::url_must_appear_exactly_once`。
这个缺陷长期未暴露，是因为此前只有 GET 类查询走过该桥接路径。

### 实测发现（与文档不符）

- **`DescribeCompShareSoftwarePort` 不含 SSH**：文档示例写
  `{"Software":"SSH","Port":22}`，实测只返回 4 个 Web 工具
  （SD-WebUI 7860 / FileBrowser 8889 / ComfyUI 8188 / JupyterLab 8888）。
  SSH 走容器实例的 `TcpForwards`（内部端口 23），**不能用这个列表判断能否 SSH**。
- **网络加速默认未开通**：影响 HuggingFace 模型下载速度。
- **机型族返回 22 条但有重复**：厂商按可用区分组后摊平，去重需自己做。
- **价格单位确认**：4090/1卡/16核/64GB 实测 Postpay ¥2.15/h、Spot ¥1.38/h、
  Day ¥47.47、Month ¥1294.75。Spot 比 Postpay 便宜约 36%。

### 实现要点

- **Base64 手写实现**（`base64.rs`）：项目无 base64 依赖，遵循「依赖极简」
  （与 `sha1.rs` 同思路）。用于重置密码编码 + `Password` 字段解码。
  RFC 4648 官方向量 + 全字节往返测试。
- **密码编码集中在 client 层**：调用方只传明文，漏编码会表现为
  「密码给了却登录失败」，且厂商只回「参数非法」，极难排查。
- **状态前置校验放驱动层**：升降配/重装/重置密码（虚机）要求 `Stopped`。
  驱动先查状态再给可操作提示（「请先执行 mangosteen cloud stop <id>」），
  而不是透传厂商的「Params invalid」。
- **容器实例区别对待**：容器可运行中重置密码；只有容器能用端口管理接口。
  一刀切要求关机会误拒合法调用。
- **`ProjectId` 缓存**：定时关机接口必填 `ProjectId`，而它不在实例信息里。
  首次调 `GetProjectList` 取 `IsDefault` 项目并缓存在驱动内。
- **定时关机最小延迟 300 秒**：厂商限制，提前拦并说明「想立刻关机请用 stop」。
- **带宽切换顶层成功≠每个成功**：厂商逐实例处理，必须检查 `Results[].Success`。

## 修复 fmtNum is not defined（上一轮误删）

### 问题
搜索时抛 `fmtNum is not defined`。原因是上一轮批量替换 JS 时，
`fmtNum` 的定义恰好落在被删区间（`refreshJobs` 附近）里，但
`renderRepos` 里的调用还在。

### 修复
在工具函数区（`esc` / `bytes` / `cny` 那一片）补回：
```js
const fmtNum = (n) => {  // 5857773 → "5.86M"，12345 → "12.3k"
  ...1e9→B / 1e6→M / 1e3→k，非数字返回 "—"
};
```

### 顺带修掉的遗留不一致
**前端还在按格式过滤仓库**（`has_gguf !== false`）。第 9 轮需求已改成
「不过滤、没有任何限制」，我只改了后端，前端漏改 → 搜到的仓库比实际少
（`qwen` 只出 53 个，实际 100 个）。已移除，现在两端一致。

### 新增两条防回归测试
- `e2e_ui_script_has_no_undefined_function_calls`
  —— 断言关键工具函数（bindHelp/fmtNum/bytes/esc/el/toast）都存在，
  且「有调用就必须有定义」。`node --check` 查不出这类问题（语法合法、
  运行时才缺符号），必须用这种符号级检查。
- `e2e_repo_search_does_not_filter_by_format`
  —— 断言前端不再有 `filter((x) => x.has_gguf` 这类过滤代码，
  同时保留 GGUF 徽标。

### 教训（第三次同类事故）
批量删除 JS 区间前，**先 grep 出该区间内定义的所有函数名**，
再逐个确认「区间外是否还有调用点」。
这已经是 bindHelp、fmtNum 两次栽在同一件事上。

## 修复对话页「模型信息」与活跃模型不一致

### 问题
对话页「模型信息」下拉列出的是**所有已下载模型**（读 `/v1/models`），
包括根本没启动的。用户选中一个未启动的模型，聊不了，也没有任何提示。
而部署页「活跃模型」是 0 个 —— 两页数据源不同，状态不一致。

### 根因两层
1. **数据源错了**：`/v1/models` 返回 `gw.models().list()`（已下载台账），
   不是运行中的实例。正确来源是 `/api/status` 的 `active`（过滤 ready）。
2. **下拉选择是摆设**：发送时硬编码 `model: "auto"`，网关 `backend()`
   永远取「第一个就绪的」，用户选谁都没用。

### 修复
- 前端：下拉改读 `/api/status.active`（与部署页「活跃模型」同源）；
  无运行模型时显示「（无运行中的模型）」+ 禁用下拉 +
  textarea placeholder 提示「请先在「部署」页启动模型」。
- 前端：发送传 `model: $("chat-model").value || "auto"`。
- 后端新增 `Gateway::active_backend_for(Option<&str>)`：
  · `None`/`auto`/空 → 原 `active_backend()`（本地优先）
  · 具体 ID → 精确匹配活跃实例（也接受去掉量化后缀的宽松匹配）
  · 匹配不到 → **明确报错**并列出当前运行中的模型
- `server::backend_for_model()`，`chat()` 改用它。
- 不静默退回 auto：静默换模型比报错更难排查（用户会以为就是这个模型答的）。

### 测试
521 项两轮全通过，零警告。新增：
- `e2e_chat_model_list_only_shows_running`
- `e2e_chat_with_stopped_model_reports_clearly`

### 实测
- 无实例：`/api/status.active` = 0，指定模型对话 → 400
  「模型 `xxx` 未在运行，无法对话。当前运行中：（无）」
- 部署后：两页都只列 `qwen2.5-0.5b-instruct:q4_k_m`，对话 200 且
  响应 `model` 字段与选中一致
