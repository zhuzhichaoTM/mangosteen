# 2026-10-24

## Mangosteen（山竹）v0.1.0 从零实现完成

按用户提供的产品基线提示词，完整交付了 Mangosteen —— 对标 Ollama 的个人级大模型部署客户端，
核心差异是「本地算力优先 + 云端算力弹性补位」。

### 技术选型决策

- **语言：Rust**（用户选择）。理由：单二进制、跨平台交叉编译友好、进程管理强，贴近 Ollama 形态。
- **交互层：CLI + TUI 双模**（用户选择）。未引入 clap/ratatui/crossterm，全部手写。
- **零第三方运行时依赖**：仅 serde / serde_json / toml / sha2 / libc / windows-sys。
  刻意**没有**引入 reqwest/ureq（用系统 curl）、axum/hyper（标准库手写 HTTP）、UUID、chrono、dirs。
  这符合提示词「禁止无依据扩展」原则，也让发布件只有 1MB。

### 七 crate 分层（严格自上而下依赖）

```
core（领域，零平台代码，零 IO）
 ← platform（唯一允许 cfg(target_os) 的地方之一）
 ← base（模型台账/配置/部署台账/访问控制）
 ← local（llama.cpp 引擎管理）
 ← cloud（多云驱动 + 编排 + SSH 隧道）
 ← gateway（评估引擎/调度决策器/协议适配/HTTP）
 ← cli（只依赖 gateway + core + base + platform）
```

### 关键设计决策（记下来避免以后重犯）

1. **CPU 可跑也算「本地可行」**。不因慢而降级上云，是否接受 CPU 由 `allow_cpu_fallback` 控制。
   避免「明明能本地跑却偷偷花钱」。
2. **引擎进程退出时不自动 kill**（`EngineHandle` 的 Drop 不杀）。用户需要服务继续在线，
   必须显式 `stop`。这是刻意为之。
3. **跨进程引擎可见性**：`deploy` 启动的引擎，`serve` 是另一个进程看不到句柄。
   解决方案：无句柄时回退到 HTTP 探活（2s 超时）；停止时按台账 PID 终止。
   这个坑很隐蔽，是 e2e 测试发现的。
4. **verify_hash 默认 false**。7B 模型 4.5GiB，登记时算 SHA-256 要数十秒，
   体验极差。改为 `models verify` 时按需计算。
5. **端口分配要跳过台账里已占用的端口**。否则进程重启后分配器从零开始，
   反复撞同一端口。
6. **SIGKILL 后不应报错**。SIGKILL 不可捕获，发出后必然终止；
   `kill(pid,0)` 仍成功只可能是僵尸态。沙箱环境常常禁止调用 `ps`，
   因此「无法判定时倾向于已终止」比报错安全。
7. **错误消息三段式**：现象 + 上下文 + 建议。降级失败必须区分
   「本地资源不足」和「本地部署失败」——用户排查方向完全不同。

### 架构约束自动化

`crates/mangosteen-cli/tests/layering.rs`（18 项）把提示词的强制约束变成可执行断言：
- C1 网关唯一收口（CLI 不得依赖 local/cloud crate，不得直连厂商 API）
- C2 平台无关（core/gateway/base 不得出现 cfg(target_os)）
- C3 推理引擎唯一（全仓不得出现 vLLM/TensorRT/SGLang）
- C4 本地优先（源码级验证 decide() 的判断顺序）
- C5 依赖方向自上而下

技术要点：扫描前必须剥离注释与字符串字面量，否则「解释为什么不用 vLLM」的注释会误判。

### 补充：预热必须在锁外执行（严重缺陷，已修）
初次实现把 `probe_version()` 放在 `gateway.lock()` 里跑，导致预热线程
**持锁 27 秒**，期间 `sysinfo` / `settings` / `status` 全部阻塞——
表现为「页面能开（静态文件不走锁），但所有 API 超时」。

`spawn_warm_up` 里只在取快照与写回时短暂持锁。
**教训：任何超过毫秒级的操作都不能在网关锁内执行。**

## 追加：新增 mangosteen-backend（优云智算 Compshare GPU 实例管理）

### 为什么单独一个 crate 而不是加 profile
优云智算的开放接口是 **UCloud RPC 形态**，与既有 REST profile 假设有四处根本冲突：
- 单一端点 `POST https://api.compshare.cn`，靠表单参数 `Action` 区分动作（不是 URL 路径）
- 认证是参数 `PublicKey` + `Signature`（`SHA1(参数拼接 + PrivateKey)`），不是请求头 Token
- 请求体是扁平表单（`Disks.0.Size=100`），不是嵌套 JSON
- 成功判定是 HTTP 2xx **且** `RetCode == 0`

签名无法用 `FieldMap` 表达，只能走「代码路径」。

### 分层定位
`mangosteen-backend` 只依赖 `mangosteen-core`，由 `mangosteen-cloud/registry.rs`
在 `driver = "compshare"` 时分流调用。新增两条架构约束守护：
- `c5_backend_is_only_reachable_through_cloud_layer`：gateway/cli/base 不得引用 backend
- `c5_backend_has_no_platform_branches`：backend 内不得出现 cfg(target_os)

两个 crate 各自有 `Transport` trait，registry 里写了 `BackendTransport` 零成本桥接，
让 compshare 与其它驱动共用同一套 curl 设施。

### 已用官方向量验证的实现
- SHA-1 自实现（工作区只有 sha2），用 FIPS 180-1 三个标准向量 + 百万 'a' 向量钉死
- UCloud 签名的官方测试向量：`cba5cf5ec4d4233d206b1b54951e3787350a642f`

### 驱动承担的三个业务补偿（上层不必认识厂商限制）
1. **创建前强制查库存**：厂商文档要求必须用 `CheckCompShareResourceCapacity`
   判库存，不能用 Describe 类接口。无库存直接返回可降级错误，不提交创建请求。
2. **销毁前先关机**：`TerminateCompShareInstance` 仅对 `Stopped` 有效。
   `destroy()` 内部完成「关机 → 等 Stopped → 删除」，否则运行中的实例永远删不掉。
3. **创建后补详情失败但 ID 必须保留**：创建只返回短 ID，`Describe` 失败时
   返回带 ID 的占位实例——否则编排器拿不到 ID，回滚无从谈起（会持续计费）。

### 单位陷阱（写进注释 + 单测钉死）
- 创建/价格接口 `Memory`：**MB**
- 机型表 `Memory`、库存接口 `Mem`、`GraphicsMemory.Value`：**GB**
混用会让显存/内存评估差 1024 倍，直接把「本地优先」的降级判断带偏。

### 测试暴露的 3 个真实缺陷（都已修）
1. **`PublicKey` 没进请求体**：`Credential::sign` 只在内部副本插入公钥用于算签名，
   真正发送的参数集缺 `PublicKey` → 真实调用必被鉴权拒绝。测试抓到的。
2. **`RetCode` 字符串形式解析失败**：厂商不同接口既返回数字 `0` 也返回 `"0"`。
   加 `de_ret_code` 宽松解析器，统一到 8 个响应结构。
3. **`is_not_found` 漏英文文案**：原来只匹配 `not_found` 码与中文「不存在」，
   漏了厂商的 `instance not found`，导致幂等销毁误报错。

### 顺带修掉的既有缺陷（原本就让 layering 测试红）
- `mangosteen-base/src/extract.rs` 内联了 `cfg!(target_os)`（选 textutil/pdftotext/Word COM），
  违反 C2。已下沉为 `mangosteen-platform/src/docconv.rs`，base 只调用不判断平台。
- e2e 的 `free_port()` 是 TOCTOU：先 bind(0) 拿号再释放、再重新 bind，
  并行跑多个测试二进制时随机 `AddrInUse`。改为 `bind_ephemeral()` 直接返回已绑定的 listener。
- cloud `net.rs` 测试写死 `20100..20110` 等固定端口区间，与其它测试进程抢占。
  改为 `port_base(offset)` 按 pid 派生唯一区间（每段 100 个端口）。

### 测试基线
726 个测试全通过（原 727 中含本轮删除/合并项），零编译警告。

- **空结果也是要验证的路径**：`UHostSet: []` 只能证明鉴权通过，

- **厂商「可选参数」不要在上层强制为必填**，否则会把业务约束泄漏进协议层。
- 自测时用占位值（如 `-`）塞参数，会被厂商当成非法值拒绝
  （`Params [Region] not available`），这也反过来证明了参数确实发出去了。

## 追加：适配 DescribeCompShareSupportZone（可用区列表）

### 接口要点（文档 + 实测差异）
文档只列 6 个字段：`Region`/`RegionId`/`Zone`/`ZoneId`/`Describe`/`IsPod`。
**实测多出两个文档未列、但很有用的字段**：
- `UnsupportedImageTypes`（数组）：该可用区**不支持**的镜像类型。
  实测容器区为 `["System","Other"]`，上海二B 为 `["Community"]`。
- `DisableImageSync`（布尔）：是否禁用镜像同步。

`UnsupportedImageTypes` 是关键发现：**它的作用等同于提前预警错误码 226603
（所选镜像不支持该卡型）**。容器可用区不支持 `System` 镜像，
而本项目默认用系统镜像 → 若不检查，会一路走到创建才失败。

### 两套 ID 不能混用
| 字段 | 类型 | 用途 |
|------|------|------|
| `Region`/`Zone` | 字符串 | **业务参数**（创建/查询实例传这个） |
| `RegionId`/`ZoneId` | 整数 | 仅厂商内部标识，业务接口不用 |

### 本轮改动

## 追加：适配 CheckCompShareResourceCapacity（全区域 GPU 库存扫描）

新增 `crates/mangosteen-backend/src/capacity.rs` + `examples/scan_capacity.rs`。

### 为什么需要「矩阵式」调用
库存接口只回答「**某可用区 + 某卡型 + 某镜像 + 某计费模式**下哪些
(GPU卡数, CPU核数, 内存GB) 组合有货」，**不支持通配符**。
要回答「全平台哪里能开到 4090」，只能逐组合问。

扫描策略（约 5+3+16=24 次请求）：
1. 查可用区（1 次）→ 过滤容器区、不支持系统镜像的区
2. 每区查机型表（每区 1 次）→ 只对该区真实存在的卡型发库存请求
3. 逐 (可用区, 卡型) 查库存 → 聚合

### 实测抓到的**最严重缺陷**
第一版扫描对 `CheckCompShareResourceCapacity` 复用了**未绑定区域**的客户端，
导致请求体里完全没有 `Region`/`Zone`——而这两个都是**必填参数**。
真实调用必被厂商判参数非法。测试断言「请求必须带 Region/Zone」抓到的。
修复：每个可用区用 `client.with_scope(transport, region, zone)` 派生客户端。

### 其他实现要点
- `ScanOptions.skip_container_zones` 默认 true（容器区不能 SSH，用不了）
- 单点失败不中断：某可用区/卡型失败只记录原因，其余继续
- `out_of_stock_types()` 区分「缺货」与「查询失败」——
  失败是**不知道**，缺货是**知道了但没有**，对用户含义完全不同
- `recommend()` 按消费级卡偏好 + 最小可用配置排序

### 真实库存（2026-10-25，Postpay，Ubuntu/Win 镜像结果一致）
| 卡型 | 有货区 | 最小可用配置 |
|------|--------|--------------|
| 5090 | cn-wlcb-01 | 1卡/16核/96GB |
| A100 | cn-wlcb-01 | 1卡/16核/64GB |
| A800 | cn-wlcb-01 | 1卡/16核/240GB |
| H20  | cn-wlcb-01 | 1卡/16核/240GB |
| V100S| cn-wlcb-01 | 1卡/10核/64GB |

**全平台缺货**：4090、4090_48G、3090、2080、P40、2080Ti
→ 项目的首选消费卡 4090 当时无货，只有 5090 可开。
→ cn-sh2-02（上海二B）所有卡型全部缺货；有货的只有 cn-wlcb-01。

### 关键发现：计费模式决定库存池
同一时刻同一镜像扫全平台：
| ChargeType | 有货卡型 |
|------------|----------|
| Postpay / Dynamic / Month / Day | 5 种 |
| **Spot** | **0 种**（抢占式库存池独立）|

→ 「查不到库存」时**先换计费模式重试**，别急着判定平台无货。

### 语义提醒
`CheckCompShareResourceCapacity` 是**模拟调度**：只证明「此刻能调度到」，
不锁定资源，真正下单前仍可能被抢。所以它是决策辅助，不是预占。

## 追加：找最便宜 GPU 并启动（真实下单验证）

### 双模式设计
`ScanScope::{Zone{region,zone}, AllZones}` —— 显式区分两种诉求：
- 单可用区：调用量 1+1+该区卡型数（约 11 次），回答「这个区能不能开」
- 全区：约 24 次，回答「整个平台哪里能开、哪里最便宜」

`scan()` 是统一入口，内部按 scope 分流。

### 新增能力
- `quotable_specs()`：只取有货组合（给缺货配置查价纯属浪费调用）
- `price_quotes()`：批量查真实价格，按元/小时升序
- `PriceBoard::cheapest()/cheapest_releasable()/sorted_by_vram_efficiency()`
- `provision_cheapest()`：**扫描 → 查价 → 逐个尝试启动**，含下单前库存复核
- `precheck_stock()`：下单前复核，返回 Available/SoldOut/Unknown

### 实测抓到的两个真实缺陷
1. **自动挑镜像挑到 Windows**（严重）
   取「第一个 Available 的系统镜像」→ 选中 `Windows-nvidia 2022`，
   开出的实例 `SshLoginCommand` 为空、无法 SSH、跑不了 llama.cpp，
   白花计费时间。厂商列表里 Windows 排在前面。
   修复：`mapping::pick_linux_image()` —— 优先 Ubuntu，其次任意 Linux，
   只有 Windows 时返回 `None`（不将就）。
2. **`PriceBoard::cheapest()` 取 `first()`**
   依赖调用方先排序。`PriceBoard` 是公开结构，测试或缓存反序列化时可能未排序，
   会让「最便宜」悄悄变成「第一个」。改为内部算 min。

### 另一个必须记住的运维事实
**库存快照会过期**：同一可用区相隔约 20 秒两次扫描，5090 从有货变售罄。
所以 `provision_cheapest` 在下单前对每个候选重新 `precheck_stock`。
`Unknown`（接口失败）不跳过——查不到 ≠ 没有，跳过可能错过唯一可用机器。
