## 修复「输出非常卡顿」：返回路径梳理

### 用户反馈
大模型输出速率非常卡顿，要求梳理返回路径，找出不合理处并优化。

### 根因分析（对照实验）
1. **直连引擎 1.32 tok/s** → 说明不只是转发问题
2. 查硬件：**Intel i7-4770HQ（2015 款 MBP，4 核 8 线程）**，无 GPU 加速
3. 查内存：**swap 已用 10 GB / 11 GB**，free 仅 230 MB → 系统级内存枯竭
4. 查部署参数：`context_size = 32768`（用户没传就用了模型原生上限）、
   `use_mlock = true`（纯 CPU 一律锁内存）

### 三个真实问题（按影响排序）

#### ① 流式被网关破坏（最严重，纯代码缺陷）
`handle_connection` 是「`route()` 返回完整 `Response` → 一次性 `write_all`」，
而 `forward_json` 用 `http_post_json` → `read_to_end` **整体读取上游**。

后果：`stream: true` 的请求要等模型把整段话生成完，网关才吐第一个字节。
25 tokens 要 10 秒，界面上就是「点发送 → 卡住 → 突然整段出现」；
这期间点「停止」也没用（网关还阻塞在读上游）。

修复：新增 `relay_stream` 直通路径，在 `handle_connection` 里
**先于 `route()` 分流**（`is_stream_request` 判定 POST + 推理路由 + `stream:true`）。
用 `curl --no-buffer --noproxy '*'` 逐行读上游（符合项目「HTTP 走系统 curl」
约定，且免去手写 chunked 状态机），逐行 `protocol::rewrite_sse_line` 改写
model 字段，再以 HTTP chunked + **每块 flush** + `TCP_NODELAY` 写给客户端。
客户端断开 → 立刻 `kill` curl，上游写失败即停止生成。

实测：**首字节从「等全部生成完」降到 0.74~3.3s**，逐块到达（12 块，间隔 ~1.3s）。

#### ② 默认上下文太激进
`assess()` 里 `req.context_len.unwrap_or(spec.native_context)` —— 用户不指定
就用模型原生上限（32768 / 128k）。KV cache 与上下文线性相关，
0.5B 按 32768 分配就有 400 MB 纯浪费。
修复：新增 `DEFAULT_CONTEXT = 8192`，未指定时取 `min(native, 8192)`。
实测 KV cache 402 MB → 100 MB，速度 1.32 → 2.04 tok/s。

#### ③ mlock 默认开启（在内存紧张时是负优化）
`use_mlock: gpu_layers < total_layers` —— 纯 CPU 一定满足，等于「一律锁内存」。
mlock 语义是「锁在物理内存不许换出」，只在内存充裕时是好事；
内存紧张时挤压系统、触发内存压缩，反而更慢。
也不能靠静态总量判断：`usable_memory()` = 总内存 - 25%，不反映当前占用。

修复：`LocalPlan::from_assessment` 默认 `use_mlock: false`；
新增配置 `local.mlock`（默认 false），由 `Gateway::deploy` 落台账前注入。
纯 CPU 用户要稳定延迟时显式开启。

### 顺带修的 bug
`relay_stream` 出错时（如无就绪实例）直接 `?` 抛给 `handle_connection`，
而那边只是 `return` —— 客户端看到「连接被关闭、无任何响应」，
前端只能报「网络错误」。改为 `relay_stream` 外层统一回写错误响应。

### 测试
906 项两轮全通过，零警告。新增：
- `stream_tests::detects_stream_requests`（判定边界：非 POST / 非推理路由 /
  缺省 stream / body 非 JSON）
- `stream_tests::rewrites_single_sse_line`（只改 model，帧结构保留）
- `stream_tests::chunk_encoding_format_is_correct`（真实 socket 验字节格式）
- `e2e_stream_request_is_relayed_not_buffered`（源码级 + 顺序保证：
  分流必须在 `route()` 之前）
- 改写 `plan::tests::cpu_plan_disables_flash_attn_and_gpu_layers`
  （旧断言「CPU 必开 mlock」与新语义冲突）
- 会话 e2e 加 `with_sessions_path` 隔离（原先写进了用户真实 `sessions.json`）

### 结论：软件问题已修完，剩下是硬件天花板
本机 2015 款 i7-4770HQ + 无 GPU + swap 用尽，纯 CPU 推理
0.6~2 tok/s 是这台机器的物理上限，不是代码能解决的。
建议用户：关掉占用内存的程序（swap 已 10 GB）、
换更小量化（q4_0）、或接受这个速度。

## 排查「什么在占内存」

### 沙箱限制与绕过
本机 shell 里 **`ps` / `top` 被沙箱拒绝**（`operation not permitted`），
`footprint` 需要 root。可用替代：
- `memory_pressure`（全局内存/压缩器/swap 统计，**可用**）
- `lsof -n -P`（可列进程，但没有内存大小）
- **`/usr/lib/libproc.dylib` + Python ctypes**（推荐）：
  `proc_listallpids` 枚举 → `proc_pidinfo(pid, PROC_PIDTASKINFO=4, ...)`
  取 `proc_taskinfo.pti_resident_size`（RSS）与 `pti_pageins`
  → `proc_name` / `proc_pidpath` 取名与路径
  脚本留在 `/tmp/memtop.py`、`/tmp/memcat.py`

### 实测结论（2026-10-26 07:30）
| 占用 | 进程数 | 分类 |
|------|-------|------|
| 4222 MB | 276 | macOS 系统（不可关） |
| 3109 MB | 25 | Google Chrome |
| 2902 + 2052 MB | 19 | **WorkBuddy（本对话客户端）** |
| 936 MB | 23 | 微信（WeChatAppEx 小程序进程居多） |
| **532 MB** | 1 | **llama-server（模型推理）** |

全局：free 仅 7 MB、wired 3.5 GB、**compressor 3.4 GB（90 万页）**、
swap used 6.8 GB、`Pages decompressed` 2.8 亿次。

### 关键反直觉发现
**llama-server 页入仅 149 次**（缺页 17 万次是 mmap 首访，正常）——
说明**模型内存并没有被换出**，推理慢不是因为它自己换页。

真正原因：
1. CPU 是 2015 款 i7-4770HQ（4 核 2.2 GHz，无 GPU 加速）；
2. 内存压缩器（3.4 GB）在抢 CPU，`Pages decompressed` 2.8 亿次；
3. 系统整体靠 swap 硬撑，UI/浏览器响应也受影响。

所以「关程序」的收益主要是**让系统不卡、给压缩器减负**，
而不是直接让 tok/s 翻倍。这点要对用户说清楚，别过度承诺。

## 网关默认端口 11434 → 11516

用户要求「API 网关默认端口是 11516，后续都用该网关启动」。

**根因**：11434 是 Ollama 守护进程的固定端口（`OllamaEngine::DEFAULT_PORT`），
网关默认占它等于和 Ollama 引擎抢端口。

改动点（5 处）：
1. `crates/mangosteen-core/src/lib.rs` `DEFAULT_GATEWAY_PORT = 11_516`（唯一来源）
2. `config/config.example.toml` `port = 11516`
3. `README.md` 三处（OpenAI 入口示例 ×2、配置片段 ×1）
4. **用户实际配置** `~/Library/Application Support/mangosteen/config.toml`
   （已备份为 `config.toml.bak-20261026-074554`）——
   改常量不改它**不生效**，因为该文件显式写了 `port = 11434`
5. `crates/mangosteen-cli/src/commands/ui.rs` 测试改用常量断言，
   不再写死字面量

顺带增强：`Gateway::new` 里 `scheduler.reserve_port(config.gateway.port)`。
因为 11516 落在引擎区间 11435-11999 内，虽然分配器有
`is_port_bindable` 兜底，但显式预留不必依赖「网关已开始监听」的时序。

**保留不动**：`engine.rs` / `plugin.rs` / `webui.rs` / `gateway.rs:1428`
里出现的 11434 都是 Ollama 自己的端口，语义正确。`dist/` 是旧版分发包快照，
未改（改了文档与其中的旧二进制不符）。

验证：906 项测试全通过、零警告；`ui --no-open`（不带 --port）直接起在
11516，对话实测 200；旧 11500 已释放；11436 的部署实例不受影响。

## 部署进度可视化（六步）

用户要求：点「部署」后要看到过程与进度，含模型评估/设备选择/设备配置/
模型下载/模型量化/启动模型等环节，并给出成功或失败的明确反馈。

### 新增模块 `gateway/src/progress.rs`

- `DeployStage`：`Assessing / Downloading / Selecting / Configuring /
  Quantizing / Launching`（`STEPS` 常量即 UI 步骤条顺序）+ 终态
  `Ready / Failed`
- `StageOutcome`：`Running / Done / Skipped / Failed`
- `StageEvent`：追加式轨迹（同一阶段可多条，前端取最后一条作状态）
- `ProgressSink<'a> = &dyn Fn(DeployStage, StageOutcome, String)`

**`detail` 用 `String` 不用 `&str`**：事件最终要存进 `Vec<StageEvent>`，
传 `&str` 每次上报都多一次 clone，且调用点 `&format!(..)` 的临时值
生命周期很别扭。踩过一次编译错误才定下来。

### 阶段顺序与直觉不同（重要）

用户列的顺序是「评估→选择→配置→下载→量化→启动」，**实际是
「评估→下载→选择→配置→量化→启动」**：`Gateway::evaluate` 要读
GGUF 元数据（层数、隐藏维度）才能算显存，文件不在本地就没法评估。

处理方式：两次「评估」（请求内预检 + 下载后资源评估）合并为同一阶段
（detail 变化、序号不回退），对外仍是 6 步。**不要**为了贴合用户
措辞去调整真实执行顺序。

### 「模型量化」为什么是 Skipped

部署链路**不做自动量化**：用户下的已是量化版 GGUF，再量化只降精度。
`base::quantize` 是 CLI 侧独立能力。如实标 `Skipped` + 原因，
不假装跑过——假装会让用户以为多花了几分钟。

### 关键实现点

- `Gateway::deploy()` 转调 `deploy_with_progress(req, &noop_sink)`，
  **签名不变**（CLI 与既有测试零改动）
- 失败上报**集中在 wrapper**：主体有十几处 `return Err`，逐个埋点必漏，
  漏掉的表现是「进度条永远卡在某一步」
- `PullJobs::set_stage` 的指针**只前进不回退**（异步事件可能乱序），
  但轨迹保留全部事件
- `set_deployment` 失败时若最后一条已是 Failed 就不再追加，
  避免「网关报一次 + 任务层报一次」两条重复
- sink 在**持网关锁**期间被调用 → 实现只能写内存任务表，
  绝不做 IO（否则下载期间整个 API 拖死）
- 前端 `startJobPolling()` 1 秒一刷、**终态自动停**；
  部署页 `unmount` 必须清 `jobTimer`

### 未覆盖的路径

「已下载模型」里的「启动」走 `POST /api/deploy`（同步请求 + 弹窗
spinner），**不产生 pull job**，所以没有六步进度。要统一得把
`/api/deploy` 任务化，但会破坏大量 e2e 断言（它们依赖同步返回
201 + deployment id），暂未做。

验证：916 项测试全通过（+10）、零警告；实测 pull+deploy 六步
全部如实呈现（下载因文件已存在标 Skipped、量化标 Skipped 带原因、
启动给出 PID 与端口）。

顺手修掉两个既有问题：
1. `lib.rs` 模块文档还写着「推理引擎唯一」，与插件化冲突 → 改为
   「引擎差异插件化」
2. `scheduler::tests::ports_rotate_across_decisions` 断言端口**连续**
   → 改为**严格递增**（并行测试占用区间内某端口时分配器跳过是正确
   行为，旧断言会偶发假失败）

## 修复：UI 卸载模型失败（percent-encoding）

用户报：想卸载 `qwen2.5-0.5b-instruct:q2_k`，卸载失败。

**根因**：模型 ID 含 `:`。浏览器 `encodeURIComponent` 把 `:` 编成 `%3A`，
后端 `parse_request` 取原始路径去匹配路由 → 404
（`未知路由：qwen2.5-0.5b-instruct%3Aq2_k`）。
同一 ID 用 `curl` 手敲冒号却正常 —— 典型的「UI 点不动、命令行正常」，
所以只在界面上暴露，之前一直没发现。

**修复**：在 `parse_request` 里对**路径**做 percent-decode
（新增 `percent_decode_path`），一处修好所有路由，不用逐个改调用点。

几个刻意取舍：
- 只解 `%XX`；`+` 在路径里是字面加号（空格是 query 的规则）
- 坏转义（`%ZZ`、截断的 `%A`）原样保留，交给路由自然 404
- `%2F` 会解成 `/`，不做特判：模型 ID 不含 `/`，路径参数只用于查
  台账 key（不拼文件路径），无穿越风险

**顺带修的第二个问题**：`remove_model` 回显请求参数
`"file_deleted": delete_file`，而 `ModelStore::remove` 在「路径不在
授权范围」时**静默跳过删除却仍返回成功** → UI 会报「已删除（含磁盘
文件）」而文件还在占几个 GB。改为删前记路径、删后核实存在性，
不一致时返回 `leftover` 残留路径；前端按 `file_deleted` 分支提示。

**注意**：验证时我自己发的 `DELETE` 请求也真的移除了台账记录
（`delete_file` 未带所以文件没删）。用 `models add <path>` 恢复了。
教训：**复现删除类 bug 前先想清楚副作用**，别在生产数据上直接试。

验证：923 项测试全通过（+7）、零警告。新增 5 项单元测试
（解码含中文/小写十六进制/加号字面量/坏转义/端到端路由）
+ 2 项 e2e（编码 ID 能路由、`file_deleted` 如实上报）。

## 部署顺序重排 + 评估输出资源占用 + 全生命周期验证

用户三点要求：① 模型评估要输出资源占用；② 下载必须排在设备选择/配置
**之后**，每步显示结果再跳下一步；③ UI 上跑通大模型全生命周期。

### 关键突破：下载前也能精确评估

原顺序「下载→评估」是被迫的：`evaluate` 要读 GGUF 元数据（层数、
KV 头数、隐藏维度），文件不在本地就没法算。解法是
**HTTP Range 只取文件头**：

- `base::download::probe_remote_metadata`：`curl --header "Range: bytes=0-N"`
- `core::gguf::parse_stream`：从字节流解析元数据段（新增 pub 入口）
- 头部**大小自适应**：先 8 MB，解析报「读取提前结束」就翻倍，
  上限 64 MB。实测 Qwen2.5-0.5B 的元数据段约 6 MB（15 万 token 的
  词表字符串表很大），4 MB 不够——一开始就是栽在这里。

**踩坑**：最初把 `--dump-header -` 和 `--output -` 都指向 stdout，
再按「最后一个空行」切分头/体。**这是错的**——GGUF 是二进制，
里面完全可能有 `\r\n\r\n` 字节序列，按它切会把元数据截断，表现为
`读取提前结束（failed to fill whole buffer）`。改成头走临时文件
（`--dump-header <file>`）、体走 stdout 限长读取。

**体为什么不能也落文件**：源若忽略 Range 返回整文件，
`--output <file>` 会老实下完 4 GiB，把「2 秒预取」变成「几十分钟」。
所以体留 stdout，读够 N 字节就杀进程（curl 被 SIGPIPE 杀掉属预期）。

### 阶段拆分（prepare / commit）

`Gateway` 新增两段式，下载夹在中间：

- `prepare_with_progress(evaluated, req, sink)` → `PreparedDeployment`
  - `Local(PreparedLocal)`：评估+选择+配置已完成，台账已落 `provisioning`
  - `Done(plan)`：云端路径，prepare 内已全部完成
- `commit_local(prepared, sink)` → `DeploymentPlan`：启动 + 健康检查

`deploy_with_progress` = prepare + commit 背靠背（模型已在本地时用）。
`pulljobs::spawn` 改成三段：`prepare` → 下载 → `commit`。

`DeployHooks { prepare, commit }` 两个闭包由 server 构造，
各自短暂持网关锁——下载期间**绝不持锁**（老坑）。

### 修复的真 bug：远端部署启动报「模型文件不存在：」

`evaluate_remote` / `evaluate_estimated` 构造的 `Evaluated.model_path`
是**空的**（文件还没下），`LocalPlan::from_assessment` 照抄空值。
启动时引擎拿到空路径，报「模型文件不存在：」——冒号后什么都没有。

修法：`PreparedLocal::with_model_path(path)`，commit 钩子用下载落地路径
补上；同时**同步更新台账**（prepare 阶段已按空路径落过盘，
不更新会让后续探活/重启拿到空路径）。有回归测试锁住。

## UI 优化 + 部署可中止回滚

用户六项要求：① 副标题去掉「GGUF」→「大模型文件」；②「搜索并部署」→

### ③ 是真功能，不是 UI 开关

「停止」要求真的停下并回滚，涉及四层：

1. **下载层可中断**（`base::download`）
   - `DownloadOptions.should_cancel: Option<CancelCheck>`（`Arc<dyn Fn() -> bool>`）
   - `run_curl` 原来用阻塞的 `wait_with_output()` → 改成 `wait_or_cancel`
     轮询 `try_wait`，收到取消就 `kill()`。stderr 单独起线程读，
     否则管道写满会让 curl 卡死。
   - 新增 `MnError::Cancelled{stage}`：与失败**必须分开**。
     混成 Network 会让重试逻辑把用户刚取消的下载又拉起来
     （`is_retryable()` 与重试循环都要跳过它）。
2. **编排层检查点**（`pulljobs`）：准备前 / 准备后 / 下载后 / 启动后
   各查一次 `is_cancelled`，命中就调 `hooks.abort` 并 return。
3. **网关回滚**（`Gateway::abort_deployment(id, Option<&Path>)`）：
   停引擎 → 释放端口（新增 `Scheduler::release_port`）→ 按需删文件
   → **删除台账记录**（不是标 destroyed，回滚要「当没发生过」）。
4. **前端**：`can_abort` 字段（只有非终态任务给停止按钮）+ 确认框
   说清「会删本次下载的文件」。

**`delete_file` 为什么传路径而不是 bool**：远端部署的 prepare 发生在
下载**之前**，台账里那条记录的 `model_path` 是空的，照它删等于什么也没删。
调用方（pulljobs）知道文件真正落在哪。同理「模型原本就在本地」时
不能删——那是卸载用户已有资产，不是「停止部署」。

### 顺带修的真 bug：僵尸 provisioning 记录永久挡住重试

下载失败 / 登记失败后，`prepare` 留下的台账记录状态仍是 `provisioning`，
而 `is_active()` 把它当活跃。唯一性检查按「同模型 + 活跃」拦人，于是
这个模型**永远无法重新部署**，报「已有活跃实例」——但那个实例根本不存在。
实测复现（源站 429 限流触发），修复：这两条失败路径都调 `abort` 清记录
（**不删文件**，`.part` 留着续传）。已加断言「回滚后同一模型必须能再次部署」。

## 部署页：按钮状态自动同步 + 成功提示去重（12:5x）

## `cloud cheapest`：封装「当前可用的最低价 GPU」查询与创建

### 为什么要单开一条路径，不能复用 `cloud pick`

`pick` 走四维打分（默认 `balanced`），「综合最优」未必最便宜——延迟/库存分
会翻盘。实测：¥2.15/h 的 4090 排在 ¥1.34/h 的 V100S 前面。用户明确说
「要最便宜的」时不能拿它凑合。

新增 `SelectionConstraints::cheapest_first`（core 层），给出**不受配置影响**的
纯价格序。排序口径抽成 `policy::cheapest_cmp`，由 `SelectionStrategy::Cheapest`
与 `cheapest_first` **共用**——两处各写一遍必然漂移，表现是
「`cloud pick` 说 A 最便宜、`cloud cheapest` 说 B」。

配套编排器方法：`CloudOrchestrator::cheapest` / `create_cheapest`，
网关 `cheapest_cloud` / `create_cheapest_cloud`。

### 「可用」由创建结果定义，不由库存字段定义

优云库存接口是**模拟调度**（对能开出来的机器也返回 false）。所以 `--create`
**不拿 `stock` 当准入条件**，按价格顺序逐个真开。2026-10-26 真实记录：

```
P40    ¥0.380 → 226604 无库存  ✗
2080   ¥0.390 → 226604 无库存  ✗
3080Ti ¥0.700 → 226604 无库存  ✗
3090   ¥1.130 → 226604 无库存  ✗
V100S  ¥1.340 → 创建成功       ✓  uhost-1wy3vbe69lkf（Running，117.50.162.129:23）
```

`create_cheapest` 与 `provision` 共用新抽出的 `create_first_running`，因此
继承了同一条不变量：**创建成功但起不来的实例必须先销毁（带重试）才换下一个
候选**；销毁失败立刻返回并带残留实例 ID，绝不继续建（会同时留两台计费）。

### 裸实例必须能被清理（否则就是持续计费的源头）

`cloud cheapest --create` 建的是裸实例：不建隧道、不传模型、**不写部署台账**。
代价是它不会被 `stop`/`abort` 自动回收。因此配套：

- `cloud destroy --instance <服务商>/<实例ID>`（`Gateway::destroy_cloud_instance`
  转 `teardown`，不要求台账里有记录）
- 创建成功后 CLI **直接打印**这条可复制执行的命令

### CLI

- `cloud cheapest`：查询，`--json` 给结构化结果，`--all` 显示全部候选
- `cloud cheapest --create [--yes] [--name x]`：不带 `--yes` 时打印费用并返回
  退出码 2（与 `destroy` 的确认语义一致）
- 修复一个实测踩到的坑：`--create` 必须登记进 `cli.rs` 的 `BOOLEAN_FLAGS`。
  否则 `--create --yes` 会把 `--yes` 吃成 create 的值 → `has("create")` 为假
  → **命令只查询不创建，还不报错**。已加守护测试。

### 测试基建：并发下引擎探测超时的假失败

全量并行跑时，断言 `preview.local_viable == true` 的用例会随机失败：
`preview` 对**空缓存**会现场探测引擎版本，预算 `ENGINE_PROBE_BUDGET`（2 秒）；
几十个用例并发抢 CPU 时假引擎脚本都可能超 2 秒 → 结论「引擎状态未知」
→ 本地判不可行。

解法：新增 `Gateway::warm_up_engine()`（**同步**预热，与后台的 `spawn_warm_up`
分工不同），e2e 侧加 `TestEnv::warmed_gateway(cfg)` 供这类用例使用。
**刻意不做成 `gateway()` 的默认行为**——有一条测试专门守护「缓存为空时接口
不阻塞」（`e2e_preview_and_doctor_do_not_probe_engine_synchronously`），
全局预热会改掉它的前提（已实测踩到）。
