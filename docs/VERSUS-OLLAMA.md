# Mangosteen vs Ollama：差异化分析

> 结论先行：**Ollama 解决"本地能跑"的问题，Mangosteen 解决"本地跑不动"的问题。**
> 前者是更好的本地运行时，后者是本地优先的算力调度层。

---

## 一、定位差异

| 维度 | Ollama | Mangosteen |
|------|--------|-----------|
| 一句话定位 | 本地大模型运行时 | 本地优先的算力调度客户端 |
| 核心问题 | "如何在本机方便地跑模型" | "本机跑不动时怎么办" |
| 假设前提 | 模型能塞进你的硬件 | 模型**可能塞不进**你的硬件 |
| 用户决策负担 | 用户自己判断能不能跑 | 由资源评估引擎判断并给出方案 |
| 算力来源 | 单一（本机） | 双源（本机 / 云端），统一抽象 |

这不是"谁更好"的问题，而是**面向不同约束的设计**。
如果你的模型永远塞得进显存，Ollama 更合适；如果你会想跑 70B 但只有 24GB 卡，
Mangosteen 的设计才开始产生价值。

---

## 二、能力矩阵

| 能力 | Ollama | Mangosteen | 说明 |
|------|--------|-----------|------|
| 本地模型部署 | ✅ 成熟 | ✅ | 两者都用 llama.cpp |
| 模型拉取（registry） | ✅ 内置 | ⚠️ 需手动放置 / 后续扩展 | Mangosteen 首版聚焦部署调度，不做模型市场 |
| 自动模型卸载 | ✅ 空闲卸载 | ⚠️ 显式 stop | 个人客户端场景下，静默卸载反而让人困惑 |
| [OI] 兼容 API | ✅ | ✅ | 两者都提供 `/v1/chat/completions` 等 |
| 资源需求评估 | ❌ 用户自行判断 | ✅ **独立引擎** | 见下文第三节 |
| 显存不足自动降量化 | ❌ | ✅ | 从 F32 向 IQ1_S 遍历找可行档 |
| KV Cache 量化降档 | ✅ 手动参数 | ✅ 自动（f16→q8_0→q4_0） | Mangosteen 在评估阶段就决策 |
| 部分层卸载 | ✅ 手动 `num_gpu` | ✅ 自动计算层数 | |
| **云端算力调度** | ❌ 无 | ✅ **核心能力** | 见第四节 |
| 多云厂商统一抽象 | ❌ | ✅ | 驱动可配置化，加厂商不改代码 |
| 节点选择（多维打分） | ❌ | ✅ | 价格/延迟/可用性/硬件四维 |
| SSH 隧道自动化 | ❌ | ✅ | 云端服务本地无感访问 |
| 部署台账持久化 | ❌ | ✅ | 防忘记关机导致持续扣费 |
| 本地文件访问控制 | ⚠️ 有限 | ✅ 白名单 + 符号链接防护 | |
| 全屏 TUI | ❌ | ✅ | 纯命令行用户可选 |
| 环境自检 `doctor` | ⚠️ 简单检查 | ✅ 逐项 + 修复建议 | |
| 桌面 GUI | ✅ macOS/Windows 应用 | ❌ 明确不做 | 见第六节 |

## 三、资源评估：从"试错"到"预判"

### Ollama 的方式

用户要么凭经验，要么直接 `ollama run` 然后看是否 OOM。
显存不够时表现为加载失败或推理极慢，用户需要自己去查文档调参。

### Mangosteen 的方式

部署前先算清楚：

```
$ mangosteen assess llama3.3-70b --context 8192
⚠ 本地无法承载该模型，需要云端算力

  模型      llama3.3-70b
  落位形态  本地无法承载
  资源需求  权重 40.2 GiB + KV 2.5 GiB + 计算缓冲 0.5 GiB + 开销 0.39 GiB = 43.6 GiB
  显存预算  24.0 GiB
  内存预算  48.0 GiB

→ 本地任何量化档都不足。云端实例至少需要 43.6 GiB 显存
```

**为什么这件事重要**：用户在做决策前就知道结果。
不需要"跑一次试试→OOM→查资料→改参数→再试"这个循环。

估算的准确性来自两个细节：

1. **KV Cache 单独计算**（而非"参数量×2"的经验法）：
   `2 × 层数 × KV头数 × head_dim × 上下文 × KV精度`
   GQA 模型与 MHA 模型的 KV 差 7 倍，只看参数量会错一个数量级。

2. **解析 GGUF 文件头获取真实架构参数**，而非让用户手填。
   手填 `n_kv_heads` 从 4 写成 28，KV 估算就差 7 倍。

## 四、云端调度：Ollama 没有的那一半

这是最本质的差异。Ollama 的架构假设"算力就在本机"，
所以它的所有抽象（模型管理、API、生命周期）都围绕单机。

Mangosteen 从第一行代码就假设"算力可能在别处"，因此：

### 4.1 多云统一抽象

```rust
trait ProviderDriver {
    fn create(&self, spec_id: &str, ...) -> Result<Instance>;
    fn start(&self, id: &str) -> Result<Instance>;
    fn stop(&self, id: &str) -> Result<Instance>;
    fn destroy(&self, id: &str) -> Result<()>;
    fn describe(&self, id: &str) -> Result<Instance>;
    fn list(&self) -> Result<Vec<Instance>>;
}
```

AutoDL / 优云智算 / 阿里云对上层完全等价。
新增服务商只需一段 TOML（端点点位 + 字段映射 + 状态映射），**不改代码**。

### 4.2 节点选择

```
$ mangosteen cloud pick --min-vram 24 --max-price 3.0 --explain
★ autodl/RTX 4090 [cn-west-1] ¥2.380/h · 42ms · 24.0GiB │ 价格 1.00 延迟 1.00 可用 0.92 硬件 0.94 → 总分 0.9654
  ucloud/RTX 4090 [cn-east-2] ¥2.650/h · 78ms · 24.0GiB │ 价格 0.90 延迟 0.54 可用 0.92 硬件 0.94 → 总分 0.8123
```

四维加权、权重可配、打分依据可解释。
用户在花钱前能看到"为什么选这个"。

### 4.3 无感访问

云端实例的推理端口经 SSH 隧道映射到本机 `127.0.0.1:<port>`。
上层应用看到的地址形态与本地部署**完全一致**：

```
本地部署：http://127.0.0.1:11435/v1
云端部署：http://127.0.0.1:11436/v1   ← 隧道映射
```

应用侧代码零改动。

### 4.4 降级链的显式性

```
$ mangosteen deploy llama3.3-70b
✓ 部署完成：llama3.3-70b (云端算力 · AutoDL)
⚠ 发生算力降级：cloud:本地资源不足：需要 43.6 GiB，可用显存 24.0 GiB
  云上实例正在计费，用完请执行 `mangosteen stop <部署ID>`
```

降级不是"悄悄发生"的。用户始终知道：
* 现在用的是哪里的算力
* 为什么没用本地
* 什么时候该停止

## 五、架构差异

### Ollama（简化）

```
CLI / API ──▶ 模型管理 ──▶ llama.cpp（嵌入为库）
```

单进程、单算力源、模型常驻内存由 scheduler 管理。

### Mangosteen

```
CLI / TUI ──▶ API 网关（唯一收口）
                 │
                 ├─▶ 资源评估引擎
                 ├─▶ 调度决策器（本地优先）
                 │      ├─▶ 本地链路（llama-server 子进程）
                 │      └─▶ 云端链路（多云驱动 + SSH 隧道）
                 │
                 └─▶ 统一协议适配（[OI] 兼容）
```

关键结构差异：

| 差异 | Ollama | Mangosteen | 影响 |
|------|--------|-----------|------|
| 引擎集成方式 | 作为库嵌入 | 作为子进程管理 | Mangosteen 可独立升级引擎、崩溃隔离 |
| 网关位置 | 进程内 | 独立层（可独立 `serve`） | 多客户端共享一个入口 |
| 算力抽象 | 无（只有本机） | `ComputeOrigin` 一等公民 | 上层永不感知来源 |
| 状态持久化 | 内存为主 | 台账立即落盘 | 进程重启不丢云端实例 |
| 失败处理 | 返回错误 | 错误分类 + 可重试判定 + 自动降级 | |

## 六、Mangosteen 明确不做的事

诚实说明边界，避免"什么都想做"导致什么都不精：

| 不做 | 原因 |
|------|------|
| 模型市场 / registry | 需要运营与审核，与"个人客户端"定位不符；用户手动放置 GGUF 即可 |
| 桌面 GUI | 产品基线明确 CLI + TUI；GUI 引入前端技术栈与打包复杂度 |
| 内置对话界面 | 基线明确"不内置对话界面、Agent 框架"，API 交给上层应用 |
| 集群 / 多租户 / 分布式推理 | 企业级能力，与个人级定位冲突 |
| 第二个推理引擎 | 本地与云端必须行为一致；多引擎会让参数体系分裂 |
| 非 GGUF 格式 | 与 llama.cpp 生态对齐，避免格式转换链 |

这些"不做"与"做"同等重要——它们保证了产品在单一场景上足够深。

## 七、什么时候该用哪个

### 用 Ollama

* 你的模型都能塞进显存（如 7B/13B 跑在 24GB 卡上）
* 你只需要一个稳定的本地推理服务
* 你希望开箱即用、不想配置
* 你需要模型市场的一键拉取体验

### 用 Mangosteen

* 你**有时**会想跑超出本地能力的模型（70B、长上下文）
* 你希望"能本地就本地，不能本地自动上云"，而不是手动在两套工具间切换
* 你需要知道自己为什么跑不动、差多少、要多大机器
* 你在意云端成本，需要选点依据与计费可见性
* 你有多个云账号，希望统一管理

### 两者可以共存

Mangosteen 的网关对外就是 [OI] 兼容接口，与 Ollama 的 API 形态一致。
上层应用可以按需切换 base URL，甚至在 Mangosteen 的部署里指向一个
由 Ollama 管理的本地服务（虽然这偏离了"推理引擎唯一"的设计意图，
但技术上没有阻碍）。

---

## 八、一句话总结

> **Ollama 让你在本地跑模型；Mangosteen 让你在本地跑不动的模型也能跑，
> 并且始终知道自己在用谁的钱。**

前者优化"本地体验"，后者优化"算力获取决策"。
两者的技术栈选择（都用 llama.cpp、都提供 [OI] 兼容 API）
恰恰说明它们不是替代关系，而是可以互补的两层。
